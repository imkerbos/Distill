# 使用手册

从零到"把一条策略推进 Git"的完整流程。部署本身见 [deployment.md](deployment.md)，
本机试玩见 [getting-started.md](getting-started.md)。

## 谁在用

| 角色 | 能做 |
|---|---|
| `VIEWER` | 看：拓扑、流量与判定、质量、安全视图、策略预览 |
| `ADMIN` | 上述全部 + 集群 / 账号 / 设置 / Git 绑定 / 采集详情 / 导出 / 写回 |

首次登录用的是**引导账号** —— 它只为"让第一次登录成为可能"而存在（建账号要先登录，
而首次登录时还没有账号）。登录后第一件事：在账号页建真正的管理员，然后改掉引导账号的密码。
任何角色都能在 `/me/password` 改自己的密码。

---

## 第 1 步：登记集群

`/clusters`（ADMIN）。

一个集群的接入状态有三档，页面上直接显示：

| 状态 | 含义 |
|---|---|
| `REGISTERED` | 登记了，还没有任何数据进来 |
| `OBSERVING` | 数据在进来，但还不足以支撑判定 |
| `READY` | 可以看结论了 |

登记时**务必把 Pod / Service 网段填对**。这不是元数据：判定一个地址属于本集群、
别的集群还是外部，靠的就是它。网段缺失或写错时，判定会退化成 `UNKNOWN` 并附上缺口原因
—— 平台刻意让它"答不出"，而不是自信地答错。

每个集群还有一个**数据来源**标记：

- `FIXTURE` —— 读内置合成数据集（demo 用的那两个集群）
- `COLLECTED` —— 读这个集群自己被采集到的数据

它由登记决定，**不由"有没有采到数据"推断**。没有写路径也不该有：
"把某个集群临时切回演示数据"不是一个安全位置，那是一句关于生产集群的假话。

---

## 第 2 步：让数据进来

两条路，选一条即可，也可以两个集群各走各的。

### A. 推送式（推荐，平台不持有集群凭据）

1. 在集群页为这个集群**签发 agent token**。**它只显示一次**，平台库里只留 SHA-256。
2. 把 token 做成 Secret，按 [deployment.md](deployment.md#三被管集群侧distill-agent)
   把 DaemonSet 装进那个集群。
3. agent 用集群自己的只读 ServiceAccount 读资产、读本节点 conntrack，推回平台。

一把 token 只绑一个集群、只能写、不能读平台任何东西，可随时吊销（`ACTIVE` → `REVOKED`）。

### B. 拉取式

把目标集群的**只读 kubeconfig** 放进凭据后端（设置页配 `DIR` 或 `SECRET_MANAGER`），
在集群上填写引用，然后跑一次 collector Job。平台主服务只存引用 —— 把引用解析成凭据
这件事只发生在 collector 进程里。

## 第 3 步：确认数据真的进来了

`/collection`（ADMIN）。这一屏答两个独立的问题：

- **资产采集**最近一次运行的状态与错误原因
- **流量摄入**最近一次的状态

两者是**两条独立链路**，各自会失败、各自重试。一个集群可以资产已经在库、流量还是零
（比如还没接上流量来源）—— 那是正常形态，不是故障。

页面显示"这个集群还没有可用的采集数据"时，先看这一屏：常见原因是资产进来了但
Pod 身份区间还没推导出来，而所有读路径都从那张表出发。

---

## 第 4 步：看现在是什么样

| 页面 | 回答什么 |
|---|---|
| `/topology` | 谁在跟谁通信，按 workload / identity 聚合，不是按 Pod 或 IP |
| `/flows` | 一条条连接，以及**当前策略对它的判定** |
| `/quality` | 这份数据本身可信到什么程度：缺口在哪、哪些判定退化了 |
| `/security` | 暴露面与风险条目 |

### 读判定：两个字段，不是一个

| 字段 | 取值 | 含义 |
|---|---|---|
| `verdict` | `ALLOW` / `DENY` / `UNKNOWN` | 当前策略对这条连接的判定 |
| `confidence` | `TRUSTED` / `DEGRADED` | 这个判定本身可不可信 |

**它们永远不合并成一个"综合分"。** "允许且证据充分"和"允许但证据不足"是两件事，
合并之后没有人能把它们分开 —— 而据此收紧策略的那个人，正需要它们分开。

`verdict = UNKNOWN` 时一定附带一个**封闭枚举**的原因，常见的几个：

| `unknown_reason` | 意味着 |
|---|---|
| `SNAPSHOT_MISSING` | 那个时间点没有对应的资产快照 |
| `IP_AMBIGUOUS` / `CLUSTER_AMBIGUOUS` | 这个地址落在多个集群网段里，或归属判不出 |
| `NAMED_PORT_UNRESOLVED` | 策略用了命名端口，而对应 Pod spec 解析不出来 |
| `EXTERNAL_NO_IDENTITY` | 对端在集群外，没有可用身份 |
| `NAT_TRANSLATED` / `IDENTITY_LOST_MESH` | 地址被 NAT 或 mesh 改写，原始身份丢了 |
| `LOG_SAMPLED_OUT` | 流量日志采样把它丢了 |
| `POLICY_MALFORMED` | 策略本身解析不出来 |
| `CCNP_PRESENT` | 存在 Cilium 集群级策略，标准 NetworkPolicy 语义不足以定论 |
| `LB_INGRESS_ADDRESS` | 这一端是负载均衡入口地址，只能按 ipBlock 表达，没有 Pod 主体——这是一条结论，不必再查采集 |

**看到 `UNKNOWN` 不要当成"没问题"。** 它的意思是这条连接的结论不成立，
据此做的任何收紧都是赌博 —— 先把原因消掉。

## 第 5 步：把现有策略拿进来

`/policy`（导入部分是 ADMIN）。三种来源：

| 来源 | 用于 |
|---|---|
| `CLUSTER` | 采集到的集群里正在生效的策略 |
| `GIT` | 策略仓库里的那一份 |
| `PASTE` | 手工贴一段 YAML |

导入的策略有两种角色：`BASELINE_CURRENT`（现状基线）与 `CANDIDATE_ADDITION`（候选新增）。

> **注意：导入今天只落库、只列出，不参与任何计算**（2026-08-25 核实）。
> 它不进候选集、不进 dry-run 预测、不进写回文件。两个角色是为将来准备的字段，
> 现在贴一条策略进来，屏幕上的任何数字都不会变。
>
> 要让一条自己写的策略真的生效，见 [policy-lifecycle.md](policy-lifecycle.md) 里的
> 「用户自定义规则」三条路径 —— 今天唯一可用的是直接写策略仓库。

## 第 6 步：生成候选与 Baseline

平台按观测到的事实生成候选策略，外加几类 Baseline（如 DNS、metrics 抓取、
LoadBalancer 健康检查这类**每个集群都需要、漏了就出事**的规则）。

**每条 Baseline 都带推导依据落库**，页面上能点开看"凭什么给你这条"。
没有硬编码的常量表 —— 一张写死的规则表在下一个集群上就是错的，而它不会报错。

要拿 YAML：策略页的导出（ADMIN）。导出的是文本，交给谁、什么时候 apply 由你决定。

### 两个旋钮

生成出来的策略不是只有一种形态。预览、导出、写回都接受这两个参数：

| 参数 | 取值 | 作用 |
|---|---|---|
| `granularity` | `WORKLOAD`（默认）/ `NAMESPACE` | 规则按 workload 各生成一份，还是折叠到 namespace |
| `namespace` | 命名空间名 | 只看/只导出这一个命名空间。**写回不接受这个参数**，见下 |

**折叠到 `NAMESPACE` 只会放宽。** 一条原本只属于某个 workload 的放行，折叠之后该命名空间里
每个 Pod 都拿到了。这是一次刻意的取舍，平台会把多放出去的量算出来（`widening`：被折叠的命名空间、
workload 数、折叠后规则数、多出的放行数），**不让它无声发生**。看到 `extraGrants` 不为零就要逐条看。

**写回拒绝 `namespace` 筛选**，会明确报错而不是默默照做：dry-run 预测按整集群计算，
一份只含单个命名空间的策略文件会带着一份把文件里没有的规则也算进去的结论。要先看单个命名空间，
用预览和导出；写回时清掉筛选。

## 第 7 步：dry-run —— 改成那样会发生什么

**这是整个平台最该慢下来的一屏。**

选定一组候选策略后，平台把观测到的连接在"新策略"下重放一遍，给出四类变化：

- 原本 `ALLOW`、改后仍 `ALLOW` —— 不受影响
- 原本 `ALLOW`、改后 `DENY` —— **会被阻断的连接，逐条看**
- 原本 `DENY`、改后 `ALLOW` —— 新放开的
- 判不出的 —— 带 `unknown_reason`

逐条确认：对每条规则可以 `ENABLE` 或 `DISABLE`，**确认之后平台会用你的决定重算一遍**。
重算的结果才是要推出去的那份。

三件要记住的事：

1. **dry-run 是默认值**，不是一个可选的预览步骤。
2. **看到一条你不认识的连接就停下来。** 平台看到的是过去某段时间的观测 ——
   一个月跑一次的批处理，可能不在窗口里。
3. **`DEGRADED` 的判定不能作为收紧依据。** 先去 `/quality` 把缺口补上。

---

## 第 8 步：写回 Git

**平台不 apply，这一步是刻意的终点。**

前置（都在 ADMIN 权限下）：

1. `/git-repos`：登记策略仓库，配好凭据引用，点**校验**。
   校验结论是封闭枚举 —— `NOT_VERIFIED` / `AUTH_FAILED` / `REPO_UNREACHABLE` /
   `BRANCH_MISSING` / `CREDENTIAL_UNRESOLVED`。**别在 `NOT_VERIFIED` 的状态下往下走。**
2. 集群页：把这个集群**绑定**到那个仓库的某个路径，同样点校验（`PATH_MISSING` 说明路径不对）。

然后写回分两步，不是一步：

| 步骤 | 做什么 |
|---|---|
| **plan** | 生成一次写回计划并落库：改哪些文件、内容是什么、基于哪个 commit |
| **push** | 人确认后，把计划推成一个分支 |

两步都落审计。**没有配写回存储的部署，两个端点都拒绝** —— 一次留不下痕迹的写回，
事后没有任何东西能回答"谁把它推了出去"。

推出去之后：**人审 PR → 合并 → Argo/Flux apply**。平台到此为止。

---

## 第 9 步：之后盯什么

- **漂移**（集群页）：Git 里的那份与集群里实际生效的那份是否一致。
  结论是 `IN_SYNC` / `DRIFTED` / `NEVER_WRITTEN` / `ANCHOR_MISSING` / `UNKNOWN`。
  `DRIFTED` 意味着有人绕过 GitOps 直接改了集群。
- **`/quality` 的缺口**：判定退化通常先于错误结论出现。
- **agent 心跳**：集群页能看到 agent 状态；长时间没有推送 = 那个集群的数据在变旧，
  而旧数据支撑的"这条规则没有流量、可以收紧"是最危险的一类结论。

## 常见问题

**为什么没有"应用到集群"按钮？**
设计如此。平台永不持有集群 NetworkPolicy 写权限 —— 出现这类代码路径视为设计错误。
代价是慢一步；换到的是变更有 PR 记录、有 review、可 revert，而且平台被攻破不等于集群被改。

**为什么这么多 `UNKNOWN`？**
因为平台不会在证据不足时替你猜。每个 `UNKNOWN` 都带原因，多数原因是可以消掉的
（补网段登记、补快照、接上流量来源）。要一个"看起来好看"的覆盖率很容易，
代价是某天一条错误的收紧建议被批准。

**能不能把 `verdict` 和 `confidence` 合成一个分数给管理层看？**
不能，这两个字段不合并。要给管理层的口径，用 `/quality` 那一屏的缺口统计。

**能不能加一个"最近 24 小时"的全局默认时间窗？**
不能。这类参数要有人填对才安全，填错了没有症状：填长了扫过量数据，
填短了漏掉真实流量并把它读成"这条规则没有流量、可以收紧"。
默认窗口由平台按每个集群实际能回答的范围现答。

**demo 集群的数字能拿去汇报吗？**
不能。`FIXTURE` 集群读的是内置合成数据集，与任何真实集群无关。
